### How to bump (mandatory for every deployed change)

1. Choose the new number: MAJOR.MINOR.PATCH. PATCH for a fix, MINOR for a new feature, MAJOR for a change that breaks existing callers of the API.
2. In the same pull request, update all of these:
   - `package.json` `version`
   - `version.json`: new `version`, `releasedAt` (UTC), `releasedAtIST`, `commit`, and a new entry at the top of `changes`
   - `CHANGELOG.md`: new entry at the top, in plain words, dated in IST
   - this Version section
3. Never deploy without the bump. Version notes live only in this repo's own git.

## Go-live knowledge (0.2.2)

- Payment chain: game -> `console.corporatetambola.com` -> Moneypenny -> IT Services (Pages + D1) -> Razorpay. One payee (IT Services), one gateway (Razorpay) in every text. Moneypenny never moves money.
- The live Worker has no payment side (`unconfiguredRail` in `src/worker.js`): `buy_credits` refuses. Connecting IT Services means a new adapter that passes `railContract` (`src/rail.js`), shipped as its own release with two audits.
- Flags `PAY_VIA_MONEYPENNY` and `PAY_VIA_CONSOLE` live in the game and console projects, not here. No customer can reach payment until D3 items 1 to 10 and D4 pass on the same run (`docs/GO-LIVE.md`). During D1 to D3 the flags are ON only behind the audited owner-only gate, which sits in front of the flag. The test runs only through that gate, and D1 must first show a non-owner account is refused. The flags are never turned ON for everyone for the test.
- Two known limits are gates before customer traffic (E5), not before the owner's test: the IT Services call inside the database transaction (freezes the lock for up to 4 s per call, and the admin sweep can chain 25 such calls, about 100 s; move it to the outbox after commit) and the name-only webhook address check (`docs/GO-LIVE.md` section 8, items 1a, 1b).
- Rollback for "paid, no credits": repeat `rail/confirm` with the order id and payment id. `credit_purchase` for INR needs a current rate and answers `rate_stale` without one. A pause also refuses payment confirmations (503), so IT Services retries. Moneypenny's own brakes: no rail wired, Hub status switch, tenant `kill_switch`, key revoke.
- Key secrets are derived from `MNP_MASTER_SECRET`: changing it kills every key. Names of secrets only, never values, in docs, tickets, chat and logs.
- Safety rules that are watched by tests: run `npm run guards` (about seven minutes on 4 cores: each guard runs the whole test suite once, and it prints progress as it goes). It must say "None are unwatched." This covers the 58 listed guards only, not every check in the code. **Known unwatched, on purpose:** `src/spend.js` line 262 (`want > left`) and line 224 (release of a captured hold). Removing either breaks no test, but no extra money can leave because the later checks at lines 272 and 225 stop it (line 262 removed would only let `hold.refunded_credits` exceed `credits`, bookkeeping only). When you add a guard, add a test that fails without it.
- A forged call is refused before it reaches the single writer (`precheckSignature` in `src/auth.js`). Logs go through `redact` (`src/util.js`), best effort, first 2000 characters only.
- Open: IT Services adapter and Pages/D1 side, owner-only gate for the test, console permanent store and 2-minute job, scheduling of sweep and event sending, Moneypenny Chat (does not exist in this repo), owner decisions in `OWNER-DECISIONS.md`.
- Test fixtures use `example.com` addresses only for new tests; older tests use `x.com` placeholders that never leave the test run.
- Payee routing (F3, dark): the migration gives a `*` route only to tenants that existed then; a later tenant needs an owner `setRoute` before the flag is turned on, or orders answer `no_route`. Routing does not read gateway health yet (F9). `processRail` still uses the old rail and does not call the payee's adapter yet (F7/F9). The payment record's payee is set at confirm only if the payment was noted first. A fallback audit row is written before the order row, so a later refusal (for example a frozen account) can leave one. `test_only` routes are used only when `ctx.testOrders` is true. Accepted limits.
- Payee owner routes and webhook (F5 to F7, dark, accepted limits): owner calls are signed with the master secret (no separate owner key class yet; a stored owner key with its own scope would need a table rebuild for the scope check). A bad-signature webhook writes at most one audit row per payee per minute (round 5) and is answered 429 per source (round 7). Intake credits through `railConfirm`, which does not write `verified_payment`; the payment record's payee is set only if the payment was noted first, as before. An ignored event is stored and a repeat of the same event id answers `duplicate`, so an owner fix needs a new event from the gateway or reconciliation (F9). Refund and dispute events are stored as ignored `not_applicable` until F8. Webhook intake needs the order's `rail_order_id` to be the gateway order id; the old stub rail uses its own ids, so only payees with a real adapter get matched. Secret names are read from the platform store by name; the Worker refuses the name `MNP_MASTER_SECRET`, but any other platform variable could still be named by the owner.
- Payee health and owner screen (F8/F9, dark, accepted limits): "stuck" in pending_rail is reported as a count and the oldest time, with no age threshold, because none was decided; the owner reads the age. Health reads the payee's own record and events only; it does not call any gateway, so it cannot tell that a gateway is down (design F9 scheduler, fallback switch and reconciliation are not built). The owner screen asks for the master secret in the page to sign calls in the browser; it is never sent or stored, but it is still the master secret typed in a browser, so a separate owner key class remains the better fix. The screen has no Terms line because it has no consent step; no Terms link address was given. Edit on the screen covers display name and note only; secret names, currencies and gateway are changed through the API. Route times are typed as milliseconds.
- Payee round 6 (dark): (1) Nested transactions are safe on both database layers (`src/db.js` and `src/do.js`): a `tx` call made on an already open transaction handle just runs the function in it. `chainRow` inside `ownerCall` or a mutator therefore joins the outer transaction, and a failure in the outer one rolls the audit row back too (test R6-1). (2) The owner nonce is taken in its own transaction BEFORE later refusals (rate limit, bad body, not found, status switch) on purpose: a refused call has used its nonce, and the caller signs a fresh one (test R6-2). (3) Webhook refusals: currency mismatch and an order already paid with another payment are final (200, stored once as ignored); a short amount and an order not yet awaiting payment are transient (409, event id not stored). A repeat event with the SAME payment id for a paid order was answered `recorded` in round 6 (no second credit); since round 7 it is `duplicate` and nothing is written. (4) `railConfirm` takes the paid transition as one guarded UPDATE before it credits; this is the safety net if a second writer ever exists, the single-writer lock already serializes today. (5) A missing or malformed signature header is 401 before any HMAC or write, so it is not counted or audited; a well-formed wrong signature still is.
- Payee round 7 (dark): (1) Rollback is shown by test, on the local database adapter and on the Durable Object stand-in (`MNP_DB=do`), not on real Cloudflare: test R7-1 makes `creditPurchase` throw after the guarded paid update (a database trigger that fires only once the order is paid) and shows the confirm route and the webhook leave the order unpaid with no credit, claim, event row or audit row, and that the retry credits once. A control in the same test shows the same fault leaves an order paid with no credit when nothing wraps it in a transaction. The first-deploy check "rollback on throw" in `STATE.md` (Known limits) stays: it has to be run on the real Cloudflare runtime. (2) Only the "payment already applied" replay is closed: a payment id already applied to its order answers `duplicate` and writes nothing. The event id header is not covered by the gateway signature, so a captured signed body can still be sent again with a fresh event id. For the ignored outcomes (`not_applicable`, `draft_payee`, `ambiguous_order`, `unmatched`, `wrong_payee` (which also adds one outbox row, the `payee.webhook_wrong_payee` event), `currency_mismatch`, `order_already_paid`) that can still add one event row and one chained audit row per fresh event id. It has no money effect (no credit, no order change). Accepted, and an OPEN ITEM (a fix would need an event id that the signature covers, or a cap on ignored rows per payee per minute). Accepted limit: because nothing is stored for a duplicate, it does not move `last_webhook_at` in the health view. (3) Bad signatures: the 429 budget is per source and payee (20 a minute), the audit row stays one per payee per minute, a good signature is never counted or refused. The source is the `cf-connecting-ip` header, which Cloudflare sets; it is folded into 64 counters per payee and never stored. Accepted limits: without that header (local runs) all calls share one counter; a caller who can choose the header can pick its counter; enough different sources fill all 64 counters and then every bad signature for that payee gets 429 (good ones still pass); no IPv6 grouping. (4) Owner nonces are kept for the 5 minute window plus 5 minutes of clock margin (`OWNER_NONCE_KEEP_MS`, counted from the time the call claims). The tenant-key cleanup in `src/auth.js` deletes the nonces of every key id after 10 minutes, so the two agree today; test R7-4 step (d) (round 8) fails if that cleanup is ever made shorter than the owner keep time (guard `tenant-nonce-cleanup-keep`). (5) The contract file now documents the answer of every payee route and `test/payee-contract.test.js` checks the real answers against it. Two routes answer HTTP 200 with `ok` false and no error object when their check fails (`secrets`, `payee_audit/verify`); that is now written down and tested, not changed. Owner decision: keep it, or move the result into its own field so `ok` always means the call worked.
- Payee round 8 (dark, test gaps and small fixes after the round 7 audits): (1) R7-4 step (d) plants an owner nonce older than the time window and younger than the keep time and checks that a tenant call keeps it; R5-5 and R7-4 take the exported times without defaults. (2) `test/payee-contract.test.js` says its scope in its header: routes and answer shapes are one-way (contract to code, a payee route that is in the code but not in the contract is NOT found); error codes are two-way (a code that a real call gives must be listed, and a listed code must be given by a real call or be on the `NOT_REACHED` list with a reason: `payee_forbidden`, `bad_json` on GET routes, `not_found` on the read route). It also checks that `recorded` carries `order_id` and `duplicate` does not, and the exact webhook error codes. Open note: the contract lists `bad_json` for GET routes, which have no body. (3) `obj()` in `src/contract.js` leaves out an empty `required` list; a test fails on one anywhere in `openapi.json`. (4) A payee whose webhook secret is missing is counted on the same per-source counter as bad signatures (500 for 20 calls a minute from one source, then 429; at most one chained audit row per payee per minute; no event row, no order change, no credit; test R8-4). Accepted: a real gateway that retries fast from one address while the secret is missing gets 429 instead of 500; the call fails either way. (5) `GATEWAYS` in `src/payees.js` is built from `ADAPTERS` (`src/gateways/index.js`): only `razorpay` can be stored, the refusal names no gateway, and no shipped file names another one (R8-5). Three older tests that used another gateway name were changed.
